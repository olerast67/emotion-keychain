# Rev B board

> **Status:** ready to order. Before release the board was corrected after a full pre-release audit and an independent review: accelerometer SA0 on VDD, REG0 output capacitance within Nordic's limit, display jumpers moved further from the header pins, charging enabled by firmware, charge-status level, TVS on VBUS, an assembly panel, JLCPCB rules for drill holes and silkscreen ([list](#pre-order-review)). Vias 0.25/0.55 mm, no vias in pads. DRC: 0 errors, 0 unconnected, 0 warnings (`out/keychain-rev-b-drc.rpt`). The fabrication files are already built: a single board in `out/`, the [assembly panel](#assembly-panel) in `out/panel/`. Before ordering, go through the ["What to check before ordering"](#what-to-check-before-ordering) list.

The keychain's own board: an nRF52840 module (Raytac MDBT50Q), Li-Po charging from USB-C, sensors, a buzzer, a vibration motor and a button. The SSD1306 0.96″ display module sits above it on the tabs of the case's acrylic frames, with the cell in between. How the circuit works and why it is designed this way is in the [hardware description](../../docs/hardware.en.md).

![Rev B board: front and back](../../docs/img/pcb-rev-b.png)

The laser-cut acrylic case and a 3D view of the assembled keychain are in [`case/`](case/README.en.md).

Everything is generated by scripts from a single description, `gen/netlist.py`: schematic, board, routing, Gerbers, BOM and CPL. Nothing is edited by hand in KiCad.

**You don't need to run anything to order.** The board `keychain-rev-b.kicad_pcb` is routed and checked, and the fab files are in `out/` and `out/panel/`; upload them as they are ([JLCPCB](#ordering-from-jlcpcb), [PCBWay](#ordering-from-pcbway)). The scripts are only needed to change the board:

```sh
cd hardware/rev-b/gen
python3 build.py place --force  # re-place parts: board WITHOUT tracks (out/work/place-*.png)
python3 build.py route     # ground and power vias, power rails, Freerouting, cleanup, fills, DRC
python3 build.py finish    # finish the routed board without re-routing: check only, nothing written
python3 build.py finish --force  # same, with writing: paste, silkscreen and labels from netlist.py, drill holes
python3 build.py fab       # DRC, Gerber, BOM, CPL, PCBWay files, drawings, previews, panel → out/, out/panel/ (needs KiKit, below)
python3 build.py panel     # board DRC, then only the panel → out/panel/ (needs KiKit, below)
python3 schematic.py       # A3 schematic + cross-check with netlist.py → out/keychain-rev-b-schematic.pdf
```

- **`place` and `route` replace the routed board:** `place` with a board without tracks, `route` with a new routing (Freerouting routes differently from run to run). So without `--force` both refuse if the board already has tracks. After `place --force` you need `route`, this time without `--force`, since there are no tracks.
- **`route` and `finish --force` write the board only after a clean DRC.** If it fails, `keychain-rev-b.kicad_pcb` is untouched, the result for inspection is in `out/work/keychain-rev-b-*-failed.kicad_pcb` and the report in `out/work/keychain-rev-b-drc.rpt`. `route` checks Java and Freerouting first and only then touches the board. `finish` without `--force` writes nothing: it finishes the board in memory, runs DRC and tells you whether the board would change.
- **`fab` runs DRC itself.** If there are errors, unconnected pads, no tracks on the board, or paste on pads of parts the fab does not place, it writes nothing to `out/` or `out/panel/`. It builds the panel before the single-board files, into a draft `out/work/panel-new`: if it fails to build or fails the checks, `out/` and `out/panel/` are untouched; if it builds, the single-board files are written and the draft replaces `out/panel/` as a whole. `build.py panel` checks the board the same way first and only then builds the panel.
- **The report `out/keychain-rev-b-drc.rpt` is written only by `fab`**, and only for a board that passed. Reports from `route` and `finish` go to `out/work/`.
- **If something goes wrong**, restore the board and files from the repository:

  ```sh
  git checkout -- hardware/rev-b/keychain-rev-b.kicad_pcb hardware/rev-b/Keychain.pretty hardware/rev-b/out
  ```

You need KiCad 7 specifically (`pcbnew` for Python and `kicad-cli`): the scripts do not work on KiCad 8 or newer. For previews and drawings: `cairosvg` (`pip install cairosvg`, the path can be given in `CAIROSVG`) or `rsvg-convert`, plus Pillow. For `route`: Java 21 and [Freerouting](https://github.com/freerouting/freerouting) 2.1, with the jar path in `FREEROUTING_JAR`. For the panel: [KiKit](https://github.com/yaqwsx/KiKit) 1.5.1 in a Python that can see KiCad 7's `pcbnew`:

```sh
python3 -m venv --system-site-packages ~/kikit-venv && ~/kikit-venv/bin/pip install kikit==1.5.1
KIKIT_PYTHON=~/kikit-venv/bin/python python3 build.py fab     # and the same for build.py panel
```

`fab` and `panel` take KiKit from the `python3` they are run with, and if it isn't there, from the Python at the path in `KIKIT_PYTHON`. Without KiKit, `fab` stops before writing anything. `build.py fab --no-panel` builds the single-board files and deletes `out/panel/`: the old panel would no longer match the board.

## Stack and dimensions

- **Board:** 30 × 46 mm plus a key-ring tab centered at the top (R4.5 semicircle, 3.2 mm non-plated hole), 4 layers, 1.6 mm, R2 corners.
- **Top 18 mm:** the nRF module with its antenna toward the right edge, and the forward-facing light sensor. Below that, the display module.
- **Stack, side view:** glass and display module board → two acrylic cell frames, the module rests on their tabs, inside them the Li-Po cell on thin double-sided tape → this board → parts on the back. No off-the-shelf standoffs.
- **Three versions, S, M and L:** cells 402025, 502025 and 602025 (~150, ~200 and ~250 mAh), 6, 7 and 8 mm under the display module (cell frames 3 + 3, 3 + 4 and 3 + 5 mm). The board and firmware are the same for all; the case screws are M2 × 25 for all. A cell fits if:

  > cell thickness + 0.3 mm (Kapton and tape under it) + 0.1 mm (Kapton on the back of the module) + 0.3 mm (swelling) ≤ height under the module − tallest part on the back of the module

  Measure the cell thickness with calipers at its thickest point. The height under the module is the two cell frames stacked, also measured with calipers: acrylic sheets vary by ±0.1–0.3 mm. To recalculate for your sheets, run `python3 case.py --sheet 3=… --sheet 4=…` in the `case/` folder. The part on the back of the module is 1.1–1.45 mm; measure your module. If it doesn't fit, go one version up. Details, including the display header and screws, are in the [case README](case/README.en.md#three-versions-s-m-l).

| Layer | What's on it |
|---|---|
| L1 (front) | nRF module, light sensor, module capacitors, cell and display header pads; long signals under the cell |
| L2 | solid ground, no splits |
| L3 | power rails: VBUS, VBAT and VSYS at 0.4 mm, VDD 0.3 mm; slow signals; all remaining space is ground |
| L4 (back) | remaining parts and signals |

Widths by net class (`NETCLASSES`):

| Class | Nets | Track | Where |
|---|---|---|---|
| Power | VBUS, VBAT, VSYS | 0.4 mm | L3 |
| Rail | VDD (3.3 V) | 0.3 mm | L3 |
| Supply | display and motor power | 0.3 mm | L1, L3, L4 |
| USB | D+, D− | 0.18 mm | L1, L4 |
| Default | signals, microphone power | 0.15 mm | L1, L3, L4 |

Currents here are up to 0.25 A; 0.4 mm on an inner layer carries about 0.7 A. Signals on L3 reference the adjacent solid ground on L2. Vias are 0.25/0.55 mm (0.15 mm annular ring): within the standard rules of both JLCPCB and PCBWay.

Routing order:

1. Every ground pad gets its own via to L2, every power pad its own via to L3, with net-class clearances.
2. Power rails on L3 are laid by a dedicated router (`gen/powerroute.py`).
3. Signals are routed by Freerouting; ground for it is the L2 plane, and the already-routed power is locked.
4. Whatever Freerouting didn't finish is routed by `gen/fixroute.py` on L1, L3 and L4 with vias, but not in component pads; stubs and dangling vias are removed.
5. Ground fills, stitching of islands, DRC.

That is why power and ground have no long, thin paths on the outer layers.

## Layout by block

- **Tab area, front:**
  - the module;
  - the light sensor, its SDA, INT and SCL pins opposite their module pins;
  - capacitors at the module's power pins.
- **Tab area, back:**
  - the buzzer behind the module, left of the antenna;
  - sensor bus pull-ups;
  - the microphone: its port opens to the front side past the capacitors;
  - the display power switch above the header pins;
  - the accelerometer.
- **Middle, back:**
  - display power-order jumpers R16–R19, in a row below the header pins, almost 2 mm from them;
  - Tag-Connect TC2030 programmer pads and test points 3V3, SYS, GND;
  - the vibration motor with its switch on the left;
  - the button on the right edge.
- **Bottom, back:**
  - USB-C with ESD protection in the middle, TVS D3 at the connector;
  - the charger on the left;
  - USB/battery power path on the right.

The module pins are chosen for this layout (`GPIO` in `netlist.py`). The sensors go to the module's left column. Display, USB, SWD, buzzer, button, vibration and charger go to the bottom row, left to right in the same order as their blocks. All signals are on the outer pads or in the wide gaps between them; no thin tracks.

**Antenna.** There is no copper on any layer under the module's antenna; this is the keep-out from Raytac's documentation (x ≥ 26, y ≤ 12.5 mm). Below it, along the right edge, run the only path for signals from the module to SWD and the button, so the keep-out was not extended downward; the board corner is open on two sides anyway. The case's top-right screw (x 26.75, y 20.2) is only 7.7 mm below the keep-out: use nylon case screws and nuts, M2 × 25 ([what to buy](case/README.en.md#what-to-buy)). If you can't find nylon M2 × 25, steel screws are acceptable for your own prototypes, but the nuts should still be nylon. For keychains you sell, nylon only. The encounter signal threshold (−70 dBm, [encounters](../../docs/encounters.en.md)) is worth checking on assembled keychains in their case.

## Power and charging

- **USB-C.** 5.1 kΩ resistors on CC1 and CC2 say "I am a 5 V sink". The USBLC6 (U3) protects the lines from static; it does not protect against an overshoot on VBUS.
- **Hot-plug overshoot.** Cable inductance and the ceramic C1 cause ringing on VBUS. According to an ngspice model it is significant only with a short, thick cable (under ~0.2 Ω including contacts) from a charger whose socket always has 5 V present: VBUS up to 6.2–6.9 V (charger 5.0–5.25 V), above 5.8 V for a few microseconds. VSYS behind diode D1 is ~0.35 V lower but may stay above 5.8 V for up to ~0.3 ms. The module's limit both on the VBUS pin (with C8 100 nF on it) and on VDDH (which is VSYS) is 5.8 V, so a brief overshoot is possible. USB-C chargers, per the standard, turn on 5 V softly and only after connection, so they don't cause this ringing; a long, thin cable damps it.
  - **TVS D3 SMF5.0A** (5 V working, 6.4–7.1 V breakdown, cathode to VBUS) sits at the connector against static and input surges; it is the clamp the MCP7383x documentation requires. It doesn't touch ringing below ~6.6 V and does not hold it under 5.8 V. It only clips peaks that would exceed the charger's 7 V limit, and even that without a guarantee.
  - The fix is to damp the ringing at J1: an RC snubber or a capacitor with ~0.5–1 Ω ESR and at least 10 µF. That would protect the module's VBUS, VDDH and the charger; a single 10 Ω resistor in front of the module's VBUS is not enough. This is planned for rev C; on the first boards the ringing is measured with an oscilloscope ([on the first boards](#on-the-first-boards)); before selling, this measurement is mandatory.
- **Charging.** MCP73832, 4.2 V, current set by R3: I = 1000 V / R3, 10 kΩ gives 100 mA. For 150–250 mAh cells (nominal) that is no more than 0.7C; what to check in the cell's datasheet is in the [case README](case/README.en.md#choosing-a-cell).
  - **Charging is enabled by firmware.** The bottom end of R3 is not on ground but on pin P0.24 (CHG_EN, module pad 48). Pin low: charging runs; pin released: PROG floats and the charger is off.
  - The firmware charges only when the nRF die temperature is between 10 and 42 °C and stops charging below 7 °C and above 45 °C (the die sensor is off by up to ±5 °C, and on USB the die is warmer than the cell, hence the margin on the cold side). The check runs immediately when USB is connected and every 30 s after that. The MCP73832 has no thermistor input, and a lithium cell must not be charged in freezing conditions. Details in the [firmware README](../../firmware/README.en.md).
  - **No firmware, no charging:** on a blank board, in the bootloader and before the firmware starts, CHG_EN is released. The board still runs from USB through D1.
  - While charging, the red LED is lit brightly.
- **Charge status.** The STAT open drain goes to pin CHG_IO (P0.20) through R5 10 kΩ, with R20 47 kΩ to ground. Read it without a pull-up and only on USB:
  - "0": charging: no higher than 0.82 V (STAT output low is up to 1.0 V);
  - "1": not charging or done: (VBUS − LED Vf) · 47/58 = 2.4–3.3 V at VBUS 4.75–5.5 V and Vf 1.45–1.75 V. On a flashed board (VDD 3.3 V) this is below the pin limit of VDD + 0.3 V. Without R20, "1" would reach 3.8 V.
  - **Unflashed board on USB** (VDD 1.8 V, pin limit 2.1 V): no charging, STAT released, and those 2.4–3.3 V exceed the limit. The pin's protection diode holds it at about 2.3 V, with up to ~0.13 mA flowing into it (from an ordinary 5 V charger, under 0.1 mA). This lasts only until the first flashing, which sets 3.3 V, and does not harm the pin. Don't leave an unflashed board on USB for long.
  - **Weak USB.** "1" reads reliably only if VBUS is at least ~4.6 V. From a weak source (an old hub, a weak power bank, a long thin cable) end of charge may read as "charging": the charging scene won't change to "charged", and the percentage stays at 99 %. The charger itself still terminates charging correctly.
  - When not charging, the LED glows faintly: 50–70 µA flow through it, R5 and R20. This is intentional.
- **Power path.**
  - With USB present, the system is powered through Schottky diode D1: VSYS = VBUS − 0.15…0.4 V, i.e. **up to ~5.4 V**. P-MOSFET Q1 is off.
  - Without USB, R6 10 kΩ pulls Q1's gate to ground, and the cell powers the system through the on MOSFET with almost no loss.
  - After USB is disconnected, Q1 turns on in ~15 ms (ngspice model; with 100 kΩ it would be ~130 ms). Until it turns on, the system runs through its body diode, and VSYS is 0.5–0.6 V below the cell. That's why the firmware ignores the cell measurement for a second and a half after disconnection.
  - On USB, R6 draws an extra 0.5 mA. In exchange, leakage of a hot D1 from VSYS into VBUS produces a 10× lower voltage across it than it would with 100 kΩ; this is worth checking on the first board in hot conditions.
- **3.3 V** comes from the module itself: the nRF52840's REG0 regulator (VDDH = VSYS, VDD is its output).
  - On a blank chip REG0 outputs 1.8 V. 3.3 V (`UICR.REGOUT0 = 3V3`) is written by the factory firmware file or by the bootloader on first start.
  - VDD has C6 4.7 µF and four 100 nF: 5.1 µF nominal. Nordic allows no more than ~5.5 µF for REG0, and at 3.3 V the ceramics lose some capacitance on top of that.
  - REG0's load is the sensors, microphone, pull-ups and buzzer: 3–4 mA against a 25 mA limit. The display and motor are on VSYS.
- **Cell charge level** is measured through the internal VDDHDIV5 divider; no separate divider is needed.
- **The display** is powered through switch Q2: the firmware turns it off completely, and R9 holds it off during reset. C11 sits between Q2's gate and drain and turns the switch on softly: according to the ngspice model, the inrush into the module's capacitors is no more than ~0.15 A instead of 0.6–1.3 A, and VSYS and 3.3 V don't sag.
- **The display module** must have an on-board LDO (662K / XC6206): it receives VSYS, which is up to ~5.4 V from USB. The module's SDA/SCL pull-ups must go to the 3.3 V LDO output; check with a continuity tester before soldering.
- **The vibration motor** is a 3 V part on VSYS (up to ~5.4 V): the firmware drives it with 20 kHz PWM at a duty cycle of 3 V / VSYS.

## Programmer (SWD)

- **J3** is a set of pads for a Tag-Connect TC2030 cable on the back, labeled SWD:
  - 1: VTref (this is the board's VDD): the programmer only *takes* the board voltage from it as a reference (the level shifter powers its keychain side from it; the current is tiny). Do not apply power to it, and do not connect it to the programmer's 3.3 V output (3V3 on the Pico): it is the output of the module's regulator;
  - 2: SWDIO, 4: SWDCLK, 5: GND;
  - 3 and 6 are not connected; reset is not brought out.
- **During flashing the board is powered from USB-C**, at the factory too. The cell may be absent at this step. On an unflashed board the charge-status pin is slightly above its limit during this; that's harmless ([charge status](#power-and-charging)).
- **The 3V3 test point reads 1.8 V until the board is flashed.** The factory file `keychain-revb-factory.hex` ([prebuilt files](../../firmware/release/README.en.md)) writes 3.3 V to UICR immediately, and after the reset at the end of flashing 3V3 is already 3.3 V. If only the bootloader is written, it sets 3.3 V itself on first start and reboots.
- **The programmer is a Raspberry Pi Pico running debugprobe firmware, through a TXS0108E level-shifter module** (~$4–6 and ~$1–2). The SWD lines go to the nRF module directly, without resistors, and the Pico only outputs 3.3 V: with the board at 1.8 V, without a level shifter it would drive current through the pins' protection diodes. So the level shifter is mandatory: its A side is powered from J3 pad 1 (VTref), its B side from the Pico's 3V3.
  - Wiring: VA → J3.1 (VTref), VB → Pico 3V3 (pin 36), OE → VA, GND → Pico GND and J3.5, A1 → J3.2 (SWDIO), B1 → Pico GP3, A2 → J3.4 (SWDCLK), B2 → Pico GP2. **Never connect the Pico's 3V3 to J3.1;** the keychain is powered from its own USB-C. Wires no longer than 10–15 cm.
  - The Pico does everything needed: the first flashing of the bootloader together with the application, erasing and removing protection, and reflashing later. After the first flashing, updates go over USB and the programmer is no longer needed.
  - **The Pico + TXS0108E combination has not yet been tested on this board:** flash one board first.
  - **Alternative: J-Link EDU Mini V2:** it handles VTref levels by itself, and the TC2030-CTX-NL cable plugs straight into it. Under SEGGER's license it is for non-commercial use only; fine for keychains you give as gifts. The J-Link EDU Mini V1 only works at 3.3 V and is not suitable.
  - **The TC2030-CTX-NL cable has no retaining clips:** J3 has no holes for latches. Hold the plug pressed evenly against J3 by hand for the whole flashing, or use the Tag-Connect retainer for NL cables (TC2030-CLIP). To the Pico the cable goes through an adapter from 10-pin 1.27 mm to 2.54 mm pins. You can also skip the cable: thin wires soldered to J3 pads 1, 2, 4 and 5.
  - What to buy, how to put debugprobe on the Pico, the full wiring, what to install on the computer, and the commands are in the [firmware README](../../firmware/README.en.md).

## Assembly panel

Parts are on both sides, and JLCPCB offers double-sided assembly only as **Standard PCBA**: a board or panel of at least 70 × 70 mm, with rails, fiducials and tooling holes. The board is smaller (30 × 52.5 mm including the tab), and almost nothing can go on two of its edges; there are no V-cuts and no rails anywhere:

- **bottom edge:** the USB-C J1 body overhangs it by ~0.7 mm, TVS D3 is 0.95 mm from the edge, and both corners have case screw holes. There is room for only one short tab on the right, between J1 and the screw;
- **right edge:** the stem of button SW1 sticks out 0.17 mm past the edge, and module U1 is 0.25 mm from the edge on purpose (antenna at the edge). No tabs here.

So the panel is ready in `out/panel/` (built by `gen/panel.py` with KiKit):

![Panel: two boards in a frame, the second rotated 180°](out/panel/keychain-rev-b-panel-front.png)

- **76 × 72 mm, two boards side by side.** The second is rotated 180°: the right edges of both face a shared slot in the middle, the bottom edges face slots by the frame.
- **Solid frame** around the boards: 5 mm left and right, 7.75 mm top and bottom (the panel is padded to 72 mm). Between the board and the frame is a 2 mm milled slot along the whole outline; no V-cut anywhere.
- **Mouse-bite tabs:** on each board's left edge (three), on the top edge left of the tab (one) and on the bottom edge on the right, between USB-C and the screw (one). So the board is held on three sides, not just at the left edge: JLCPCB recommends tabs on different sides of the board. Holes 0.6 mm, 0.4 mm between hole edges, as JLCPCB recommends. The left tabs are 5, 5 and 3 mm (5, 5 and 3 holes), the top one 4 mm (4 holes), the bottom one 3 mm (3 holes). The narrow ones are where there's little room at the edge: between R3 and R4, next to C15, and between J1 and the screw (2.5 mm to the J1 body, slot corner radius 1.5 mm from its overhang). JLCPCB recommends 5 holes or more, but ten tabs for two small boards is plenty. The holes sit in the tab itself, centered 0.25 mm outside the board edge: the board's fills are 0.3 mm from the edge, and the drill comes no closer than 0.25 mm to copper.
- **Copper at the tabs.** The ground fills on all layers have a 0.3 mm cutout from the edge at each tab. There is no board outline across the tab, and without the cutout any refill (the B key in KiCad, DRC with refill) would bring ground right up to the break line. `gen/panel.py` checks this itself during the build, because KiCad's DRC doesn't see it: mouse-bite holes no closer than 0.25 mm to copper, copper no closer than 0.3 mm to break lines, and the same on a copy of the panel after refilling.
- **On the frame:** 3 fiducials on both sides (1 mm copper, 2 mm mask opening, centered 5 mm from the panel edges; JLCPCB asks for no closer than 3.85 mm) and 4 non-plated tooling holes of 1.152 mm in the corners (JLCPCB standard). No other copper on the frame.
- **Reference designators on the panel include the copy number:** `R1_1` on the left board, `R1_2` on the right, rotated one. That's what the panel's BOM and CPL expect.
- **Panel DRC:** 0 errors and 0 unconnected (`out/panel/keychain-rev-b-panel-drc.rpt`), and the same for the refilled copy.

**Tab stubs.** After breaking out, bumps of up to ~0.3 mm remain on the board edge (up to the line of hole centers and a bit further if the tab broke unevenly). File or sand them flush with the edge: the board edge in the case must be smooth, as in the case model. Where they are, in board coordinates (mm from the top-left corner of the 30 × 46 rectangle, tab not counted):

| Edge | Where |
|---|---|
| left (x = 0) | y 3.25–8.25, 24.5–29.5 and 35.2–38.2 |
| top (y = 0), left of the tab | x 2.5–6.5 |
| bottom (y = 46), between USB-C and the right screw | x 22.0–25.0 |

There are no stubs on the right edge or on the tab.

The single board without a panel (`out/keychain-rev-b-gerbers.zip`) is for ordering bare boards without assembly.

## Ordering from JLCPCB

You don't need to run anything: the files are already in `out/panel/`.

1. **Assembly files (panel):**
   - `out/panel/keychain-rev-b-panel-gerbers.zip`: the panel;
   - `out/panel/keychain-rev-b-panel-bom-jlcpcb.csv` and `out/panel/keychain-rev-b-panel-cpl-jlcpcb.csv`: BOM and CPL for both boards on the panel.

   Bare boards only, without assembly: `out/keychain-rev-b-gerbers.zip`.
2. **PCB:** 4 layers, 1.6 mm, ENIG finish (buttons and Tag-Connect pads last longer), black solder mask, no impedance control. Vias 0.25/0.55 mm, holes of different nets no closer than 0.5 mm. Standard silkscreen: 1.0 mm text, 0.16 mm line.
   - **Order number** (Mark on PCB): choose **Order Number (Specify Position)**; in the old form this is "Remove Order Number" → **Specify a location**. JLCPCB then prints the number in place of the `JLCJLCJLCJLC` marker. The marker is silkscreen on the front under the cell (x 10–20, y 25.8 mm), on every board, i.e. on both copies on the panel. The cell and the display module cover it. Without this choice the fab puts the number wherever it sees fit and may ignore the marker, and the board is visible through the transparent case. "Remove Mark" (no number at all) also works but may cost more; the form will show the price.
3. **Panel:**
   - Delivery Format: **Panel by Customer**, one design per panel;
   - size 76 × 72 mm;
   - **PCB Qty is in panels**, two boards each. JLCPCB's minimum is 5: 5 panels are 10 boards. How many of them to assemble is set separately, under assembly;
   - Edge Rails / Fiducials and Tooling Holes: **Added by Customer**: the frame, fiducials and holes are already in the files;
   - in the order comment:

     > Customer panel 76 x 72 mm, 2 boards. Routed slots with mouse-bite tabs only; no V-cut anywhere. Frame, fiducials, tooling holes and all tabs are in the files. Please do not add any rails, tabs or V-cuts: the USB-C connector overhangs the boards' bottom edges and the side button overhangs their right edges. The only bottom-edge tab is the short one between the USB-C connector and the corner screw hole (on the rotated copy it appears at the top, left end).
4. **Assembly:**
   - you need **Standard PCBA**: parts on both sides;
   - **PCBA Qty is also in panels**, minimum 2 (4 boards). For example, PCB 5 and PCBA 3 means 6 assembled boards and 2 bare panels. The form shows how many boards you'll get;
   - BOM and CPL from `out/panel/`;
   - order the MDBT50Q module and the B3U-3100P button through Global Sourcing or consign your own: they are not in the LCSC catalog;
   - CPL rotations are computed by JLCPCB's rule: for the back side the angle is mirrored (180° − θ), then the part correction is applied. **The corrections are best guesses**: the public tables (KiBot, kicad-jlcpcb-tools, Fabrication-Toolkit) disagree on them, and nobody has verified them on our order (the table and reasoning are in `gen/fab.py`). SOT-23 (Q1–Q4): 180°, as JLCPCB's preview shows it according to user reports; SOT-23-6 (U3): −90°. **U2 (SOT-23-5, C38066): −90°, a guess:** JLCPCB's SOT-23-5 footprints are rotated inconsistently, and it needs either −90° or 180°, and we haven't seen which footprint C38066 uses. **USB-C J1 (C165948): 180°** according to two older tables, but the only report of a preview check (which we couldn't verify) says 0°, i.e. a 180° turn. **U2 and J1 are the first candidates for rotation.** SW1 and U1 (Global Sourcing) have no correction at all: JLCPCB draws their footprints itself. So **in JLCPCB's preview, check the pin-1 marker of every polarized part, on both copies on the panel** (`_1` and `_2`, the second rotated 180°), and rotate whatever doesn't match there. Then enter the exact correction by LCSC number in `JLC_PART_ROTATION` in `gen/fab.py` (how to compute it is explained there) and rebuild with `build.py fab`: the next order will go out with correct angles. What to check:
     - **back side:** against `out/panel/keychain-rev-b-panel-assembly-bottom.png` (single board: `out/keychain-rev-b-assembly-bottom.png`): Q1–Q4, U2, U3, U4, U6, D1, D2, D3, LED1, J1 and SW1. SW1's stem must point outward, past the board's right edge: on the panel drawing, into the shared middle slot for both copies; on the mirrored single-board drawing, to the left. SW1's two large pads are at the edge, the small one faces inward. A flipped J1 is obvious immediately: the shell legs don't line up with the holes;
     - **front side:** against `out/panel/keychain-rev-b-panel-assembly-top.png` (single board: `out/keychain-rev-b-assembly-top.png`): U1: the pin-1 triangle, the side without pads (antenna) toward the board's right edge; U5 (LTR-303): the pin-1 marker. U5's 2 × 3 pads are symmetric, so only the marker reveals a 180° rotation;
     - a 180° error is fatal for Q1, U2, U3, U4, D1 and D3: a reversed TVS D3 is a forward-biased diode across VBUS. With a reversed U5 the sensor's ground lands on SENS_SDA, and the whole sensor bus, accelerometer included, won't work;
   - microphone U6 has a bottom port: ask them not to wash the board, or to cover the port.
5. **By hand** you solder the display module, the cell and the vibration motor ([below](#hand-assembly)). Jumpers R16 and R18 are placed by the fab; pads R17 and R19 have no paste. This order includes no firmware: do the first flashing yourself ([programmer](#programmer-swd)).
6. **Boards are broken out of the panel** at the tabs, and the stubs are sanded flush ([where they are](#assembly-panel)).

## Hand assembly

The whole assembly follows the steps of the [case assembly](case/README.en.md#assembly): that is the only detailed procedure, together with the [first power-on](#first-power-on) checks. The cell lies under the display module, and the module covers its pads, so the order is exactly this: firmware, display jumpers, motor, cell, then the display. Everything soldered on the board near the cell is done before it.

In short, with the same step numbers:

1. Flashing and checking on USB-C only.
2. Display power-order jumpers according to the module's labels: R16 + R18 or R17 + R19, never both pairs. Before the motor and the cell, USB disconnected, with a soldering iron, not hot air.
3. Vibration motor into the VIBRO circle on the back.
4. USB-C legs and panel tab stubs flush.
5. Display module: long header for M and L, Kapton on the back of the module and on the flex cable.
6. Off-state current of the keychain while there is no cell, then the cell, using the template from the lower cell frame. No more hot air near the board after this.
7. Power-off with a 3 s button press.
8. Cell frames.
9. Module on screws with washers, solder the header pins.
10. Continuity check VCC–GND, VCC–SCL, SCL–SDA, SCL–GND and SDA–GND before power-on, then the button and the face.
11. Case, steps 11–18: microphone tube, display frame, washers, cover, back (both parts of the back frame are glued to the bottom with film), nuts, check.

A keychain that is going out as a gift gets `factory yes` in the console as the very last step after assembly and checks ([commands](../../firmware/README.en.md)): it returns to factory state and powers off.

## First power-on

The checks follow the [case assembly](case/README.en.md#assembly), each at its own step. The keychain console is USB, 115200 baud, any terminal: Arduino IDE serial monitor, `pio device monitor -b 115200`, PuTTY or `screen` ([how to open it](../../firmware/release/README.en.md)). The greeting at power-on is printed once and usually doesn't reach the terminal: the port appears when the keychain has already started. So the checks use the `ver` and `sensors` commands, which answer at any time. The test points are on the back, three round pads labeled GND, SYS and 3V3 (TP3, TP2, TP1). What to do if things aren't as expected is [below](#if-something-is-wrong).

- [ ] **USB-C only, no cell and no display** (step 1, right after flashing).
  - SYS = VBUS − 0.15…0.4 V (up to ~5.4 V). 3V3 ≈ 1.8 V on an unflashed board, ≈ 3.3 V after flashing and reset.
  - `ver`: `Прошивка <версия>, плата rev B` ("Firmware <version>, board rev B"). The version is the same as in [`firmware/release/`](../../firmware/release/README.en.md); on a keychain for sale, the tag of your sale build, without `-dirty`.
  - `sensors`: the first line is `Ускорение: x …` ("Acceleration: x …") or «Ускорение: нет новых выборок» ("Acceleration: no new samples"; then repeat), but not «Акселерометр не отвечает» ("Accelerometer not responding"); the second line starts with `Свет: есть` ("Light: present"), not `Свет: нет ответа` ("Light: no response"). This is how the accelerometer and light sensor are checked on every board.
  - Charge LED: on an unflashed board it is not brightly lit; it may glow faintly. With firmware but no cell it may blink: the charger is looking for a cell. Charging is checked later, with the cell.
- [ ] **Off-state current below 25 µA** (step 6, before soldering the cell, on every board). You need a Nordic PPK2.
  - PPK2 in source mode (Source meter), 3.7 V. With thin wires: VOUT to the BT1 "+" pad, GND to "−". USB disconnected.
  - The firmware starts by itself, without the display. Hold the button for 3 s, wait 15 s (farewell scene and sound) and record the current over 60 s. The average must be below 25 µA.
  - Unsolder the wires: the pads stay tinned for the cell.
  - A µCurrent or another ammeter goes in series between a 3.7 V source and BT1 "+", not instead of the source. An ordinary multimeter won't do: when it switches range the circuit breaks, and the keychain powers on again.
- [ ] **J2 continuity check** before the first display power-on (step 10 of the [case assembly](case/README.en.md#assembly)).
- [ ] **Face** (step 10, after the continuity check). Pressing the button: loading, then the face. The face is clean, with no stripe or garbage at the edge.
- [ ] **Charging** (with the cell, on USB). At 10–42 °C die temperature the LED is lit brightly until the cell is charged; `sensors` reports «USB да, заряжается да» ("USB yes, charging yes").
- [ ] The rest (sensors, sound, encounters) per the [firmware checklist](../../firmware/README.en.md).

**Empty cell and storage.** The keychain powers itself off («Ячейка почти пуста — выключаюсь», "Cell almost empty, powering off") while the cell still has ~3.6 mAh left before its protection board cuts off. A powered-off keychain draws 6–17 µA (the test limit is 25 µA), so this reserve lasts 9–25 days. After that the cell discharges deeper, which damages it. Charge the keychain within a week. For long-term storage leave it about half charged and top it up every 2–3 months. The calculation is in the [power budget](../../docs/power.en.md).

### If something is wrong

| What you see | What to do |
|---|---|
| **SYS around 0 V** on USB-C | Use a USB-A → USB-C cable from a computer: a USB-C charger with a C–C cable provides 5 V only when it sees the 5.1 kΩ resistors on CC, and with bad J1 soldering it doesn't see them. Inspect J1's soldering under a magnifier. If 5 V is present on capacitor C1 (back side, [assembly drawing](out/keychain-rev-b-assembly-bottom.png)) but not on SYS, diode D1 is at fault |
| **SYS present, 3V3 around 0 V** | Unpower the board and check continuity 3V3–GND (TP1–TP3). A short beep is the capacitors charging; a long one is a short. A short or unsoldered module on a factory-assembled board is an assembly defect: send the board and photos to the fab |
| **3V3 stays at 1.8 V** after flashing | 3.3 V was not written to UICR: a file without the bootloader and UICR was flashed (`keychain-revb.hex`, `firmware.hex`), or there was no reset. Flash the factory file specifically, `keychain-revb-factory.hex` (your own build: `firmware-factory.hex`), with `--reset`, then unplug and replug USB. Check: `nrfjprog -f nrf52 --memrd 0x10001304` must show `FFFFFFFD`. With the Pico: `pyocd cmd -t nrf52840 -f 100k -c "read32 0x10001304"` must give `FFFFFFFD`. |
| **No KEYCHAIN drive** | After `keychain-revb-factory.hex` there shouldn't be one: the keychain starts the firmware immediately. The drive appears only in the bootloader: hold the button and, without releasing it, plug in USB right away (within 10 s of pressing), or use the `dfu` command in the console. No drive and no console port: a "charge-only" cable (use another one) or J1 soldering |
| **No face** after pressing the button | Power off the keychain and unplug USB. Compare the labels on the module (`GND VCC` or `VCC GND`) with the jumpers, step 2 of the case assembly (if the cell is already installed, the jumpers can only be redone after unsoldering it); a module powered with reversed polarity may have burned out. Inspect the soldering of the J2 pins under a magnifier and check their continuity as in step 10 |
| **Distorted face:** stripe, garbage at the edge, picture shifted | Most likely the module uses an SH1106, not an SSD1306: the keychain firmware works only with the SSD1306 ([display](../../docs/hardware.en.md)). Replace the module with an SSD1306 0.96″; test modules from a new batch on the stand first ([what to check](#what-to-check-before-ordering)) |
| Console: **«Шина экрана зажата: SDA или SCL в нуле или замкнуты между собой»** ("Display bus stuck: SDA or SCL low or shorted together"; printed once, usually at power-on) | The keychain runs without the display: the console, charging and button power-off work. Power it off (button 3 s) and unplug USB. Look for a solder bridge between the J2 pins (SCL–SDA, SCL or SDA to GND) under a magnifier and remove excess solder with wick. Check continuity SCL–GND, SDA–GND and SCL–SDA: a few kilohms between SCL and SDA is the module's pull-ups, which is normal. No short: the module is faulty, replace it. If the line «Шина экрана зажата посреди работы» ("Display bus stuck during operation") repeats, the module is unreliable as well |
| **The face was there and disappeared** | Dark for more than a minute means pocket mode: the display is off. Light, a touch or the button brings the face back |
| **Charge LED not brightly lit** (only glowing faintly or not visible), cell present, USB connected | Console «Заряд не идёт: … °C» ("Not charging: … °C") or `sensors` shows a temperature below 10 °C or above 42 °C: the die is too cold or too hot; warm up or cool down the keychain, it checks every 30 s. KEYCHAIN drive visible: no charging in the bootloader; unplug and replug USB. `ver` answers «Не знаю такую команду» ("Unknown command") or `sensors` reports «Акселерометр не отвечает»: the firmware may be old and doesn't charge; flash a new one ([prebuilt files](../../firmware/release/README.en.md)). `sensors` reports «заряжается нет» ("charging no") and the face shows full charge: the cell is already charged |
| Charging keeps going, percentage stuck at **99 %** | Weak USB (below ~4.6 V on the board): end of charge reads as "charging" ([charge status](#power-and-charging)). Use another charger or a shorter cable |
| **Off-state current above 25 µA** | First make sure the keychain is really off: the display is dark, the console is silent, the current doesn't jump every few seconds. If it is off, it's a leak: accelerometer SA0 not on VDD, or D1 and R6 at VBUS. This is an assembly or part defect: don't sell such a board |

### On the first boards

These measurements are done once on the first boards of a batch, not on every keychain.

- **Measurement board.** Current with the face shown, in pocket mode, and off-state current with the display are measured on one board without a cell. Assemble it per steps 1–10 of the case assembly, but without the cell: in step 6 only the current measurement; step 7 is not needed (without a cell the board is unpowered anyway). PPK2 in source mode, 3.7 V, to the test points on the back: VOUT to SYS (TP2), GND to GND (TP3). To the board this is the same as a cell: without USB, switch Q1 connects SYS to the cell pads. The points are accessible until the back frame and bottom are fitted. **While the PPK2 is connected, do not plug in USB:** from USB, SYS is higher than 3.7 V, and current will flow into the PPK2 output. A cell can be added to this board later only by desoldering the display.
  - What to measure and for how long: see the [power budget](../../docs/power.en.md) and the [firmware checklist](../../firmware/README.en.md).
  - Off-state current with the display must also be below 25 µA. If it's noticeably higher than for the same board before the display, current is leaking through the display pins while the switch is off.
- **VBUS ringing on hot-plug** ([why](#power-and-charging)). **This measurement is mandatory before selling**; for your own prototypes the risk is accepted, and without an oscilloscope it can be postponed. You need an oscilloscope of at least 50 MHz (you can borrow one at a makerspace), with a ground-spring probe instead of a long ground lead. Points: module VBUS on C8 (front side, next to the nRF module), VSYS on TP2.
  - On 2–3 boards right after step 1 of the case assembly: the board is flashed, no cell or display yet, both points accessible. On an assembled keychain you can't reach them anymore: C8 is covered by the display module, TP2 by the back frame and bottom.
  - Single-shot trigger on a rising edge at 5.5 V; timebase 2 µs/div for VBUS and 50 µs/div for VSYS.
  - Use the shortest, thickest cable you can find (worst case: a short 3 A USB-A → USB-C cable). Plug in USB 10 times into each of: a phone charger with a USB-A socket, a computer port, a power bank, and the charger you will recommend to buyers.
  - Record the peak and the time above 5.8 V. **Pass:** the peak on both C8 and TP2 no higher than 5.8 V (the module's limit on VBUS and VDDH).
  - **Above 5.8 V:** don't sell it like this. Either recommend to buyers only the charger and cable the measurement passed with (per the model, a USB-C charger with a C–C cable or a long thin cable), state this in the leaflet and on the card in the box, and repeat the measurement with them. Or wait for ringing damping at the connector in rev C ([plan](../../docs/plan.en.md)); a rework of rev B only if verified by the same measurement.
- **Charger near end of charge.** C1 and C2 are 10 µF 0603; under voltage their capacitance drops to ~4–5 µF, near the MCP73832 minimum (4.7 µF). With an almost full cell, scope C2 (VBAT) and C1 (VBUS), both on the back: the trace must be flat, with no sawtooth or sine wave above 0.1 V. At the end of charge the LED goes out and stops blinking. If it oscillates, save the scope capture: it's an item for rev C.
- The display on an almost empty cell and the light sensor with a bright display: see the [firmware checklist](../../firmware/README.en.md).

## What to check before ordering

- [ ] Dimensions of the display module you bought: `OLED` in `gen/footprints.py`: board, header row, holes. The height of the tallest part on the back of the module: the clearance above the cell depends on it.
- [ ] Display module with an LDO and pull-ups to 3.3 V (see ["Power"](#power-and-charging)).
- [ ] Display module is a 0.96″ SSD1306: the keychain firmware drives the display only as an SSD1306. 1.3″ modules are usually SH1106 and won't work. If you have the [ESP32 stand](../../firmware/README.en.md), before soldering test one module from each seller and each batch on it: a clean face means it fits; clean only after the `h` command means SH1106, not suitable for the keychain.
- [ ] Cell: thickness per the [S, M, L versions](#stack-and-dimensions) rule, protection board, wire placement (`CELL`). No wider than 20.7 mm and no longer than 25.0 mm including wrap and protection board: the pocket in the frames is 21.0 mm, and at the top the cell is held by the plastic of the header. Many "402025" cells are actually up to 20.5 × 25.5 mm; one that long won't fit ([case README](case/README.en.md#choosing-a-cell)). From the cell's datasheet: maximum charge current at least 100 mA, charge temperature range covering 0–45 °C, or at least 7–45 °C.
- [ ] TVS D3 SMF5.0A: in JLCPCB's BOM tool, part number C1509112 must come up as SMF5.0A in a SOD-123FL package and be in stock. Otherwise choose another SMF5.0A in SOD-123FL. The other LCSC numbers are already verified (marked "✓" in `gen/netlist.py`).
- [ ] DRC: `out/keychain-rev-b-drc.rpt`: 0 errors, 0 unconnected, 0 warnings; for the panel, `out/panel/keychain-rev-b-panel-drc.rpt`. Both reports are written by `build.py fab`, and only for a board that passed. If you changed the board, `out/` must be built after the last edit.
- [ ] Panel: order "Panel by Customer" from `out/panel/`, comment text from [ordering from JLCPCB](#ordering-from-jlcpcb). No V-cuts or rails anywhere, tabs only those in the files: none on the right edge, one short one on the right of the bottom edge.
- [ ] Quantities at JLCPCB: PCB Qty in panels, minimum 5; PCBA Qty is how many panels to assemble, minimum 2. Two boards per panel.
- [ ] JLCPCB order number: **Order Number (Specify Position)** ("Specify a location"): the number lands on the `JLCJLCJLCJLC` marker under the cell ([order](#ordering-from-jlcpcb)).
- [ ] Rotations of polarized parts in the fab's preview, on both sides and on both copies on the panel, U2 and J1 first (their corrections are guesses): back side (Q1–Q4, U2, U3, U4, U6, D1, D2, D3, LED1, J1, SW1) against the back assembly drawing, front side (U1, U5) against the front drawing. Put any corrections you find into `JLC_PART_ROTATION` (`gen/fab.py`).
- [ ] USB-C plug: the opening in the bottom and the back frame fits a standard plug overmold, up to 12.35 × 6.5 mm, with 0.5 mm margin. From above, the plug is limited by the lower cell frame: it has no opening, and the cell's end is covered. Plugs up to ~6.4 mm pass; a 6.5 mm plug touches the frame and may not go in all the way ([USB-C plug](case/README.en.md#layers-from-face-to-back)). Check the cables you will recommend on an assembled keychain.
- [ ] Case screws M2 × 25 nylon and nylon nuts; steel screws only for your own prototypes if nylon can't be found, and then check the encounter threshold in the case. For sale, nylon only.

## Pre-order review

- **Pre-release audit** (what changed on the board):
  - Accelerometer SA0 (U4, pin 7) on VDD, address 0x19. On ground, 0.11–0.16 mA would flow through the internal pull-up all the time, even in a powered-off keychain. The firmware also disables that pull-up (CTRL_REG0 = 0x90).
  - C6 is 4.7 µF 16 V (CL10A475KO8NNNC, C19666), C14 and C15 are 100 nF: REG0 output capacitance within Nordic's limit.
  - The R16–R19 row moved down from y = 21.6 to y = 23.0 mm: bare pads of another net almost 2 mm from the J2 pins.
  - R3 is on CHG_EN (P0.24): charging only when the firmware allows it.
  - R20 is 47 kΩ: charge-status "1" no higher than 3.3 V from any USB source.
  - D3 SMF5.0A on VBUS, against static and input surges; it does not limit hot-plug ringing ([above](#power-and-charging)).
  - Cell and motor pads have no paste: the wires are soldered by hand.
  - Not included in rev B and moved to the [rev C plan](../../docs/plan.en.md): VBUS ringing damping at the connector (instead of 10 Ω before the module's VBUS pin), 100 Ω in the SWD lines, the antenna keep-out extended further down the right edge.
- **Independent review** (what changed after the audit):
  - The assembly panel in `out/panel/` ([above](#assembly-panel)): without it, Standard PCBA can't be ordered at JLCPCB.
  - The pads of DNP jumpers R17 and R19 have no paste: the stencil doesn't print solder on them, so a blob can't short the display power. The same for all parts not in the CPL; `fab` checks this.
  - Holes of different nets no closer than 0.5 mm (JLCPCB rule): the rule is in `keychain-rev-b.kicad_dru`, and DRC sees it. Three vias moved by 18–40 µm; the smallest clearance is now 0.512 mm. The routers (`build.py`, `fixroute.py`) also respect this rule.
  - Silkscreen text 1.0 mm, line 0.16 mm (JLCPCB minimum 1.0 and 0.153 mm), no closer than 0.15 mm to mask openings: G/V of the display jumpers, 3V3/SYS/GND, SWD, OLERAST, "+"/"−" of the cell and motor, 1/2/SCL/SDA of the display header. The G/V labels were moved above the jumpers: there was no room below R19. Test point and display header labels use a narrow character (0.75 mm) so the words don't run together. Part outlines from the KiCad library remain 0.12 mm lines.
  - Footprint silkscreen is clipped at the board outline, and U6's pin-1 marker at R8's mask opening. DRC no longer reports warnings.
  - The JLCPCB CPL gained a correction for USB-C J1, and the SOT-23-5/6 correction (U2, U3) is now −90° (for U2 and J1 these are guesses; see [ordering from JLCPCB](#ordering-from-jlcpcb)); the preview checklist now also includes SW1 and the front-side parts U1 and U5.
  - `place` does not overwrite a routed board without `--force`, `route` checks Java and Freerouting before starting, `fab` writes no files without a clean DRC.
- **Final review** (what changed after the independent one):
  - The JLCPCB order-number marker `JLCJLCJLCJLC` on the front under the cell, and the "Order Number (Specify Position)" choice in the order: the number won't end up in plain sight. Quantities in the order are in panels, PCB minimum 5, PCBA minimum 2.
  - The panel's fifth tab is on the bottom edge, between USB-C and the screw: the board is held on three sides. Cutouts in the fills at the tabs: a refill won't bring copper to the break line; `panel.py` checks the copper at the tabs itself.
  - `build.py panel` and `fab` check the board before `out/panel/` is touched and build the panel into a draft; if that fails, `out/` and `out/panel/` stay as they were. `route` without `--force` doesn't touch a routed board, `route` and `finish --force` write the board only after a clean DRC, `finish` without `--force` only checks. Only `fab` writes the report in `out/`.
  - The rotation corrections for U2 and J1 are labeled as guesses, and `gen/fab.py` has a table of exact corrections by LCSC number (`JLC_PART_ROTATION`), to be filled in after the first preview.
- **Values:** "100k" in the BOM had LCSC number C25086, which is not 100 kΩ (at LCSC/JLCPCB it is 1 Ω). On R6, R7, R9 and R15 this would have shorted VBUS, and the display and vibration motor wouldn't have worked. Now it is C25741 (0402WGF1003TCE, 100 kΩ, basic part). New values: 47 kΩ is C25792, 4.7 µF is C19666.
- **Analog section:** based on ngspice models (AO3401A/AO3400A, B5819W, 1N4148WS, the LED, the nRF pins' protection diodes): display turn-on, power transition when USB is disconnected, hot-plug overshoot, the motor switch, buzzer current per pin (peak 2.3 mA, standard drive is enough). The ngspice circuits are not in the repository; the numbers here are estimates and are worth checking with an oscilloscope on the first board. The CHG_IO levels are calculated with the formula above.
- **Connections:** the schematic, board and `netlist.py` match on every pin; the module pins match the firmware's `board.h` and `variant.h`; the NFC pins and reset are unused; there is no copper in the antenna keep-out.
- **The firmware on this board** runs fully in simulation: models of every IC, two boards and the radio link between them ([firmware README](../../firmware/README.en.md)).
